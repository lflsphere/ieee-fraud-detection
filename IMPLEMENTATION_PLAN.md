### Official data schema (for reference throughout)
- `transaction` and `identity` are separate files joined on `TransactionID`.
  **Not all transactions have identity rows** — the join must be a left join
  from `transaction`, and missingness from the join itself is a feature
  worth testing (does having no identity record correlate with fraud?).
- **`TransactionDT` is a timedelta from an unknown reference datetime, not
  a real timestamp.** Relative ordering (for chronological splits) is
  still valid, but absolute calendar features (true hour-of-day, real
  day-of-week, holidays) are **not directly recoverable** — any such
  feature is an assumption (e.g., "assume `TransactionDT=0` is midnight of
  some Day 0") and must be labeled as such, not presented as ground truth.
- **Categorical features — must be explicitly encoded, not treated as
  numeric even where values look numeric:**
  - Transaction: `ProductCD`; `card1`–`card6`; `addr1`, `addr2`;
    `P_emaildomain`; `R_emaildomain`; `M1`–`M9`
  - Identity: `DeviceType`; `DeviceInfo`; `id_12`–`id_38`
  - Everything else in the `V*`/`C*`/`D*` blocks is treated as numeric
    unless EDA shows otherwise.

## Phase 1 — Data Generating Process (DGP) — 10%
- Define the unit of analysis: one row = one transaction (`TransactionID`), with `card1`–`card6`/`addr1`/`addr2`/device fields acting as noisy proxies for the true latent entity ("account" or "device"), since no explicit customer ID exists.
- State the DGP explicitly: fraud is generated by an adversarial process (fraudsters actively adapt to detection), which is fundamentally different from a stationary natural process — this must be argued, not assumed.
- Enumerate latent variables: true identity behind `card`/`addr`/`id_*` columns, merchant risk, and the (unobserved) fraud-detection rules already in place at transaction time (the labels reflect a **historical detection policy**, not ground truth fraud rate — an important bias to name).
- State plainly: this is a **predictive**, not causal, model. No claim is made about *why* fraud happens, only about which transactions resemble historically-flagged ones.
- Name collection biases: `isFraud` labels are themselves the output of a prior detection/investigation process (selection bias — undetected fraud is mislabeled as legitimate).

**Deliverable:** `reports/final/01_dgp.md` (or notebook section) — 1–2 pages, explicit assumptions list.

## Phase 2 — Exploratory Data Analysis
- Class imbalance: quantify `isFraud` rate; visualize with log-scale where needed.
- Distributions of `TransactionAmt`, `TransactionDT`, key `V*`/`C*`/`D*` engineered anonymized features; correlation structure within `V*` blocks (many are near-duplicate/PCA-like — worth clustering, ties into Phase 4).
- Missingness patterns, especially in `id_*`/device columns — is missingness informative (MNAR) rather than random? (Likely yes — worth testing "is-null" as a feature.)
- Subpopulation check: does fraud rate vary meaningfully by `ProductCD`, device type, email domain?

**Deliverable:** `notebooks/02_eda.ipynb` with interpretation text under every plot, not just the plot.

## Phase 3 — Feature Engineering — 10%
- Temporal: transaction recency/frequency per `card`/`addr` proxy-entity within rolling windows (careful — see leakage note below).
- Aggregated: count/mean/std of `TransactionAmt` grouped by proxy-entity, computed **only from past transactions relative to each row's timestamp**.
- Interaction terms: `card × ProductCD`, `addr × device` combinations flagged by EDA as fraud-differentiating.
- Nonlinear transforms: log(`TransactionAmt`); binned `TransactionDT` — label any hour-of-day/day-of-week feature explicitly as an *assumed* calendar alignment, since `TransactionDT` is a timedelta from an unknown reference, not a real timestamp.
- Categorical encoding: `ProductCD`, `card1`–`card6`, `addr1`, `addr2`, `P_emaildomain`, `R_emaildomain`, `M1`–`M9`, `DeviceType`, `DeviceInfo`, `id_12`–`id_38` must be explicitly encoded (target/frequency encoding fit only on training folds, or tree-native categorical handling in LightGBM/XGBoost) — never left as raw strings/numeric-looking codes.
- Identity-join feature: an `has_identity_record` flag (whether a `TransactionID` matched an `identity` row) — test whether the join itself carries signal.
- For every feature, document in comments/markdown: what it captures, expected bias/variance effect, and whether it risks leakage (explicit leakage checklist, feeding Phase 8).

**Deliverable:** `src/features/build_features.py` + a feature dictionary (`reports/final/03_feature_dictionary.md`) explaining the "why" for each feature, as the assignment explicitly requires.

## Phase 4 — Unsupervised Learning & Representation
- Cluster the `V*` block (or a PCA/UMAP projection of it) with K-means and/or hierarchical clustering; check cluster stability across `k` and random seeds.
- Check whether cluster membership aligns with `isFraud` rate (without using the label to fit the clustering — unsupervised must stay unsupervised).
- Feed the resulting cluster ID (or distance-to-centroid) into Phase 5 models as an additional feature — the assignment explicitly asks you to connect unsupervised results to downstream supervised modeling.

**Deliverable:** `src/unsupervised/cluster_v_features.py`, stability plots in `reports/figures/`.

---

## Phase 5 — Supervised Learning Models
- **Linear baseline:** logistic regression with class-weighting (interpretability baseline — required).
- **Classical ML:** XGBoost or LightGBM (handles imbalance well via `scale_pos_weight`, handles mixed sparse/dense anonymized features natively).
- **Neural network:** a simple feed-forward net (tabular) with class-weighted loss; document architecture choices explicitly (why this depth/width).
- Explicitly discuss where the linear model fails (nonlinear interactions among `V*`/`C*` features) and where the NN is likely to overfit given the low fraud rate.

**Deliverable:** `src/models/{linear,gbm,nn}.py`, one shared training entry point, results logged consistently (same metrics, same CV folds) for fair comparison.

## Phase 6 — Neural Network Training & Practice
- Track train/val loss curves per epoch; save to `reports/figures/`.
- Diagnose overfitting explicitly (train/val divergence point) and describe what regularization was applied (dropout, weight decay, early stopping) and its effect.
- Brief hyperparameter sensitivity check (e.g., learning rate, hidden width) — a small grid or a couple of ablations is enough; the point is to *discuss* sensitivity, not exhaustively tune.

**No Transformer model.** Not required for Option 5 per the assignment, and explicitly out of scope for this project — do not build one, even as a stretch goal. Time saved here should go toward Phases 8–9 (leakage audit and presentation), which carry more/critical grading weight.

**Deliverable:** loss-curve plots + a short training-dynamics write-up.

---

## Phase 7 — Model Evaluation & Validation — 15%
- Use **stratified** train/test split (imbalance-aware) and **time-based** validation (transactions are timestamped — a random split risks temporal leakage; prefer a chronological holdout or time-aware CV).
- Metrics: PR-AUC (primary, given severe imbalance — ROC-AUC alone is misleading here), plus F1 at a business-relevant threshold, plus a calibration check if time allows.
- State explicitly what's being measured: generalization to *future* transactions, not just in-sample fit — tie back to the chronological split choice.
- Ensure the pipeline (CV fold generation, metric computation) is scripted, not manual, for reproducibility.

**Deliverable:** `src/evaluation/evaluate.py`, a results table comparing all 3 models on identical folds/metrics.

---

## Phase 8 — Data Leakage Analysis — 5% (but can zero out other sections if ignored)
Explicitly document, in a dedicated section, each of:
- **Preprocessing leakage:** any scaler/imputer/encoder fit only on training folds, never on the full dataset before splitting.
- **Feature leakage:** aggregation features (Phase 3) computed using only past-relative-to-row data — show a worked example of a feature that *would* have leaked (e.g., using a full-dataset mean instead of a trailing mean) and why it was avoided.
- **Temporal leakage:** justify the chronological split from Phase 7 here explicitly as the leakage-prevention mechanism, not just an evaluation choice.
- Include one concrete "before/after" example: a feature or split decision that initially leaked, and the fix — this is the single highest-signal thing you can show a grader for this section.

**Deliverable:** `reports/final/08_leakage_audit.md`.

## Phase 9 — Comparative Analysis, Recommendation & Presentation — 30%
- Comparison table: linear vs. GBM vs. NN vs. (cluster-augmented variants) on PR-AUC/F1, training cost, and interpretability.
- Explicit recommendation: which model you'd deploy and why (likely GBM — best accuracy/interpretability/cost tradeoff for tabular fraud data; NN rarely wins on tabular data at this scale, which is itself a valid, defensible finding to report, not a failure).
- Discuss tradeoffs honestly: interpretability vs. performance, latency/cost vs. marginal PR-AUC gain.
- Final write-up assembled into a single narrative document (not just concatenated notebook outputs) — since this section is 30% of the grade, budget real time for polish, not just content.

**Deliverable:** `reports/final/09_comparative_analysis.md` + a top-level `reports/final/REPORT.md` (or exported PDF/slides) that stitches Phases 1–9 into one coherent narrative.

## Note — researching other participants' approaches
The IEEE-CIS Fraud Detection competition overview
(https://www.kaggle.com/competitions/ieee-fraud-detection/overview) has an
active discussion board and public notebooks where past participants (top
solutions included) describe their feature engineering and modeling choices.
Reading these for **inspiration and sanity-checking** (e.g., "did others also
find `V*` features redundant," "what aggregation windows did the winning
solution use") is reasonable and can strengthen the DGP/feature-engineering
write-ups. However:
- Any technique adopted must be **independently justified** in this project's
  own write-up (Phases 1/3/8) — do not cite "the top Kaggle solution did X"
  as the justification on its own.
- Do not copy code verbatim from public kernels; reimplement in this repo's
  own style so the leakage-safety guarantees (Phase 8) can actually be
  verified against this project's own pipeline, not inherited blindly.
